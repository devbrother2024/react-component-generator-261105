# commit: 변경사항 분석 → 논리 단위 분류 → 한국어 커밋

## 모드

| 모드 | 호출 | 동작 |
|------|------|------|
| 자동 모드 (기본) | `/commit` | 승인 단계 없이 계획을 출력하고 바로 커밋 |
| 승인 모드 | `/commit --confirm` | 커밋 계획을 보여주고 승인을 받은 뒤 커밋 |

사용자가 "확인받고 커밋해줘", "커밋 전에 보여줘", "승인받고 커밋해줘"처럼 말하면 `--confirm`과 동일하게 승인 모드로 처리한다.
모드는 해당 요청 1회에만 적용된다. 다음 `/commit` 호출은 다시 기본(자동 모드)이다.

## 워크플로우

### Step 1: 변경사항 분석

아래 명령을 **병렬로** 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 커밋 스타일 참고 (커밋이 없으면 에러 무시)
```

- untracked 파일은 `git status` 목록의 파일명과 내용을 Read로 확인한다.
- 변경사항이 전혀 없으면 "커밋할 변경사항이 없습니다"라고 알리고 종료한다.
- 이미 staged된 항목이 있으면 사용자가 의도적으로 올린 것일 수 있으므로 Step 2 분류에 그대로 반영한다.

### Step 2: 논리적 단위로 분류

변경 파일을 **하나의 목적 = 하나의 커밋** 기준으로 묶는다.

- 서로 다른 목적(기능 추가 + 버그 수정 + 설정 변경)은 별도 커밋으로 분리한다.
- 같은 목적에 속한 코드·테스트·타입 변경은 한 커밋으로 묶는다.
- 한 파일 안에 여러 목적이 섞여 있으면 `git add -p` 대신(인터랙티브 불가) 파일 단위로 가장 가까운 쪽에 묶고, 섞였음을 사용자에게 알린다.
- 의존 순서가 있으면(예: 타입 정의 → 사용처) 의존되는 쪽을 먼저 커밋한다.

### Step 3: 한국어 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 용도 |
|------|------|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 빌드·설정·의존성·문서 등 기타 작업 |

규칙:
- 요약은 **한국어**, 50자 내외, 마침표 없이 명사형/동사 어간으로 끝낸다. (예: `feat: 컴포넌트 생성 API 엔드포인트 추가`)
- "무엇을"보다 **"왜/무엇이 달라지는가"**가 드러나게 쓴다. 파일명 나열은 피한다.
- 본문은 요약만으로 부족할 때만 쓴다. 한 줄 공백 후 변경 이유·영향을 한국어로 적는다.
- 기존 `git log`에 이미 따르는 스타일이 있으면 그것을 우선한다.
- 시스템 컨텍스트에 커밋 attribution(Co-Authored-By 등) 지침이 있으면 메시지 끝에 그대로 추가한다.

### Step 4: 사용자 승인 (`--confirm` 승인 모드에서만 필수)

**자동 모드(기본)이면 이 단계를 건너뛰고** 계획만 한 번 출력한 뒤 Step 5로 진행한다. 단, 아래 경우에는 자동 모드여도 멈추고 사용자에게 확인한다.

- 민감 파일(`.env`, 키·토큰·자격증명)이 변경 목록에 있을 때
- 한 파일에 여러 목적이 섞여 분류가 불확실할 때
- 변경 파일이 비정상적으로 많거나 대용량 바이너리가 포함됐을 때

**승인 모드(`--confirm`)에서는 승인 없이 절대 커밋하지 않는다.** 아래 형태로 계획을 보여주고 승인을 요청한다.

```
다음과 같이 N개의 커밋을 만들려고 합니다.

1. feat: 컴포넌트 생성 API 엔드포인트 추가
   - server/index.ts
   - server/routes/generate.ts
2. chore: eslint 설정 추가
   - eslint.config.js
```

- 승인 / 수정 요청(메시지 변경, 분류 변경) / 취소 중에서 응답을 받는다.
- 수정 요청이 있으면 Step 2~3으로 돌아가 반영 후 다시 승인을 받는다.

### Step 5: 커밋 실행

승인된 계획(자동 모드에서는 Step 4에서 출력한 계획)대로 커밋 단위마다 순서대로 실행한다.

```bash
git add <해당 커밋의 파일들>
git commit -m "$(cat <<'EOF'
feat: 요약

본문
EOF
)"
```

- 파일은 **이름을 명시해서** add 한다. `git add -A` / `git add .`는 쓰지 않는다.
- 이미 staged된 다른 파일이 커밋에 섞이지 않도록, 각 커밋 전에 `git diff --staged --name-only`로 확인한다.
- pre-commit hook이 실패하면 원인을 보고하고 수정한 뒤 **새 커밋**으로 다시 시도한다. `--no-verify`, `--amend`는 사용자가 요청하지 않는 한 쓰지 않는다.
- 모두 끝나면 `git log --oneline -N`으로 결과를 보여주고 `git status`로 남은 변경이 없는지 확인한다.

## 금지 사항

- `--confirm` 승인 모드에서 사용자 승인 전 `git add` / `git commit` 실행 금지 (기본 자동 모드는 예외)
- `git push`는 사용자가 따로 요청하지 않는 한 하지 않는다
- `.env`, 키·토큰·자격증명, 대용량 바이너리, `node_modules`, `dist` 등은 커밋 대상에서 제외하고 발견 시 사용자에게 알린다
- `git config` 변경, `--force`, `reset --hard` 등 이력을 파괴하는 명령 금지
